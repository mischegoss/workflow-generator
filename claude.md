# Workflow Generator — Completion Spec (v4.2 / Path B)

## 0. Document status and audience

Authoritative spec for the workflow generator's task-aware, three-stage
gated flow. v4.2 supersedes v4.1.

**v4.2 reflects what was actually built.** The original v4 / v4.1
architecture (composer, slot-filling Decomposer, scaffold map) is preserved
in §5–§9 as the long-term north star, but the as-built system uses the
**Path B simplification** documented in §5.0 and Addendum C: atomic-only
task taxonomy, freeform Decomposer (no slot filling), no composer, no
scaffold map. The task layer provides Gate 1 legibility but does not feed
the Decomposer or replace pattern-library-based skeleton building.

The shift to Path B was a scope decision, not an architectural
disagreement. Full v4 still describes the right end state. Path B is the
shippable subset that gets the user-visible wins (telemetry, gates, task
preview, Mermaid, outcome reporting) without the upstream taxonomy and
scaffold work that v4 requires.

Folds in:

- Task taxonomy as Gate 1 display backbone (Path B: atomic-only)
- Pre-existing pattern-library scaffolds for skeleton building (unchanged
  from v3)
- v3 freeform Decomposer (carried forward, not narrowed)
- Internal-beta scope (terser UX, telemetry-first, desktop-only)
- Tier 1 determinism additions (template passes)
- Three-gate architecture with Mermaid viz
- No LLM prompt validator (six deterministic checks only)
- Telemetry as product, not polish
- Catalog enrichment (`task_type`, `module_type`, `node_type`,
  `is_orphaned` per activity) plus a soft system-bias signal on
  flex-slot and fallback retrieval. See §9 and Addendum B.
- **(v4.2)** Path B implementation reality. See §5.0 and Addendum C.

Companion documents for history:

- `determinism_analysis.md`
- `plan_review_accuracy_focus.md`
- `frontend_beta_design.md`
- `finished_product_review.md`
- `task_mining_report.md` (generated by `mine_task_taxonomy.py`)

Primary goal: **produce accurate workflows by matching prompts to tasks
first for legibility, with deterministic middle stages for structure, and
narrowed LLM roles for semantic fields.** Telemetry measures how well
this works.

## 1. Architectural thesis

### 1.1 The core idea

Today's pipeline decomposes a prompt into arbitrary steps, then retrieves
activities per step, then tries to wire them. Each stage has variance. The
variances compound — Decomposer picks wrong intent, retriever picks wrong
activity, wiring picks wrong predecessor.

The original v4 pipeline inverted this by matching the prompt to **tasks**
first, where each task owned a **pre-wired pattern**. Task patterns brought
structure, members, and wiring as a unit; the LLM's job shrank to filling
slots.

**Path B keeps the user-visible half of that vision** (task-level Gate 1
preview, deterministic gates, telemetry) **and defers the architectural
half** (composer, scaffold map, slot-filling Decomposer). Pattern matching
and skeleton building remain pattern-library-based as in v3.

### 1.2 Why the user-visible wins still ship

Even without the composer, three v3 problems get partial mitigations from
Path B's other v4 components:

**Wrong activity choice.** System bias on flex retrieval (§9.2) addresses
the dominant v3 failure mode (INTERNAL plumbing winning over system-bound
activities). Task-canonical retrieval narrowing remains future work for
when the composer ships.

**Wrong wiring.** Existing pattern-library scaffolds and the Stage 4c.6
deterministic wiring pass already pre-wire the most common cases.
Wiring_map.json fires authoritative rules for matched src→tgt activity
pairs.

**Structural mismatch.** Pattern matching against pattern_library.json
produces validated skeletons for matched cases. Decomposer freeform mode
remains for unmatched cases.

### 1.3 Why this matters for UX

Gate 1 becomes legible. Instead of:

```
1. Create a table          [Tables]
2. Read server list        [Files/Folders]
3. Count servers           [Tables]
4. For each server         [Flow Control]
   4a. Get server name     [Tables]
   4b. Ping                [Network]
   4c. Check result        [Flow Control]
        4c.1. Send email   [Communication]
```

It reads:

```
Plan (5 tasks):

  1. Read data from a file
     → Load structured data from a file on disk
  2. Iterate over rows in a table
     → Loop through each row of a table
  3. Check the state of a system or service
     → Probe an external system
  4. Branch on a condition
     → If/else branch
  5. Send an email
     → Send an email via SMTP, Exchange, or platform email module

[Looks good]  [Needs changes]  [Show activities]  [Show raw]
```

The user confirms intent at the task level. They can drill down via
`[Show activities]` to see the underlying step list.

Note: in Path B, the task labels and descriptions come from the
taxonomy and are independent of the Decomposer's step list. The task
matcher and Decomposer run in parallel; preview.py weaves their outputs
together. Per-prompt-tailored task descriptions (the `→ {short_description}`
the original spec example shows) are deferred to when the composer ships.

## 2. Target architecture

### 2.1 Seven execution phases, three user-facing gates

```
User prompt
    │
    ▼
┌─────────────────────────────┐
│ Phase 0: Prompt validation  │  ← 6 deterministic checks
└─────────────────────────────┘
    │ valid
    ▼
┌─────────────────────────────┐
│ Phase 1a: Task matching      │  ← Path B: labels for Gate 1 only
└─────────────────────────────┘
    │
    ▼
┌─────────────────────────────┐
│ Phase 1b: Decomposer (LLM)   │  ← Path B: freeform (v3 mode)
└─────────────────────────────┘
    │
    ▼
╔═════════════════════════════╗
║ GATE 1: Task-level preview  ║
╚═════════════════════════════╝
    │ approved
    ▼
┌─────────────────────────────┐
│ Phase 2b: Deterministic middle│ ← v3 pattern matching + skeleton
│   (Phase 2a composer DEFERRED)│   building + retrieval + enrichment
└─────────────────────────────┘
    │
    ▼
╔═════════════════════════════╗
║ GATE 2: Activity list + flow║
╚═════════════════════════════╝
    │ approved
    ▼
┌─────────────────────────────┐
│ Phase 3: Narrowed Wirer +    │  ← emails, queries, sanity check
│          artifacts           │
└─────────────────────────────┘
    │
    ▼
╔═════════════════════════════╗
║ GATE 3: Final artifacts     ║
╚═════════════════════════════╝
```

In Path B, Phase 1a's output is metadata for Gate 1 display. The
Decomposer (Phase 1b) does NOT consume task_match_result — it reads the
prompt directly and produces a freeform step list as in v3. The composer
(Phase 2a) does not exist.

### 2.2 Endpoint set

| Endpoint                         | Phases    | Purpose                                |
| -------------------------------- | --------- | -------------------------------------- |
| `POST /plan`                     | 0, 1a, 1b | Validate + match tasks + decompose     |

| `POST /outcome/{tracking_token}` | —         | Post-import outcome reporting          |
| `GET /health`                    | —         | Liveness                               |

### 2.3 Retry policy

Unlimited retries per gate, logged for telemetry. Explicit "Start over"
button. Internal beta captures retry patterns as signal.

In Path B the existing CorrectionPipeline (Wirer-only retry on validation
or activity-count-guard failure) carries forward unchanged from v3.

## 4. Phase 0 — Prompt validation

Unchanged from v3. Six deterministic checks. No LLM validator.

1. Length (≥10 chars initial, ≥5 feedback)
2. Character diversity (≥5 distinct, unique/total ratio ≥ 0.3)
3. Consonant run (no 6+ consecutive consonants)
4. Domain keyword (≥1 from 64-word vocabulary in
   `data/prompt_validation_keywords.json`)
5. Session freshness (4-hour timeout)
6. Prompt-per-session limit (50 max, runaway protection only)

Implementation module: `tools/prompt_validator.py`. Backend and frontend
both run checks 1-4; backend adds 5-6.

**Status:** ✓ Built and verified. 13/13 smoke tests pass.

## 6. Phase 1b — Decomposer

### 6.0 Path B scope (v4.2)

**Decomposer stays in v3 freeform mode.** The slot-filling instruction
described in §6.2 is not deployed because there are no slot schemas to
fill (Path B taxonomy has none).

`mode: "freeform_fallback"` is what `agents/pipeline.py` emits in
`decomposer_call` telemetry events. `mode: "slot_filling"` would only
fire if §6.2's instruction were deployed.

The fallback path described in §6.3 is therefore the ONLY path in Path B.

### 6.1 Purpose (v4 vision)

The Decomposer's job in v4 is fundamentally different. It doesn't decide
structure (the task matcher does that). It doesn't pick activities (task
scaffolds do). It binds concrete values from the prompt to the abstract
slots each task defines.

### 6.2 Instruction (v4 vision, NOT deployed in Path B)

New instruction in `agents/decomposer_agent.py`:

```
You are given:
1. A user's workflow prompt
2. An ordered sequence of matched tasks, each with:
   - task_id
   - label
   - slot_schema: a dict of slot names and what they mean

For each task, fill in the slot_values from the prompt. If a slot isn't
answerable from the prompt, leave it as null and the user will resolve it
at Gate 2.

Do not:
- Add or remove tasks
- Reorder tasks
- Decide activities
- Invent slot values not grounded in the prompt

Return:
{
  "workflow_summary": "one-line summary of the whole workflow",
  "matched_tasks": [
    {
      "task_id": "...",
      "slot_values": {
        "slot_name": "value from prompt or null"
      }
    },
    ...
  ]
}
```

### 6.3 Fallback path (the ONLY path in Path B)

When Phase 1a returned `fallback: "use_decomposer_freeform"`, the
Decomposer runs in its v3 mode: freeform step decomposition with the old
instruction. Output flows directly into Gate 1 as before. Telemetry
marks these sessions distinctly.

In Path B, Phase 1a never sets `fallback: "use_decomposer_freeform"`
(it sets `fallback: "no_task_match"` when zero phrases match, or `null`
when phrases match). But the Decomposer still runs in freeform mode in
both cases because there's nothing else for it to do.

The freeform Decomposer output schema is unchanged from v3:

```json
{
  "steps": [
    {
      "step_id": "s1",
      "intent": "...",
      "control_flow": "...",
      "zone": "...",
      "description": "..."
    }
  ],
  "variable_contract": {
    "variables": [{ "name": "...", "type": "...", "source": "..." }],
    "loop_type": "While | none",
    "loop_source": "..."
  },
  "complexity": "simple | moderate | complex",
  "estimated_activity_count": 8
}
```

### 6.4 Telemetry events

- `decomposer_call` — { duration_ms, prompt_tokens, output_tokens,
  mode: "slot_filling" | "freeform_fallback" }
- `task_slot_filled` — { task*id, slots_filled, slots_null }
  *(Path B: not fired in real runs.)\_

## 7. Gate 1 — Task-level preview

### 7.1 Preview rendering

Function in `tools/preview.py` → `build_task_preview(match_result,
decomposition, prompt, include_activities=False) -> str`.

Path B task-centric format (no slot values inline because Path B has no
slot extraction):

```
{first sentence of prompt — used as workflow summary in Path B}

Plan ({task_count} tasks):

  1. {task_label}
     → {description from taxonomy}
     (matched "{phrase}", "{phrase}"; confidence 0.XX)

  ...

Notes:
  • Unmatched in prompt: "{segment}"

[Looks good]  [Needs changes]  [Show activities]  [Show raw]
```

The `[Show activities]` toggle drills down to the Decomposer's freeform

tasks (matcher and Decomposer run independently).

The `→ {short_description}` line uses the static taxonomy description,
not a per-prompt-tailored summary. v4 vision was prompt-tailored
descriptions; Path B uses static. When the composer ships, this can
become tailored.

The `{workflow_summary}` is the prompt's first sentence (truncated at
120 chars), not an LLM-generated summary. v4's slot-filling Decomposer
would have produced a real summary; Path B uses the prompt as a
stand-in.

### 7.2 Fallback-mode preview

When the matcher returns `fallback: "no_task_match"`, the preview falls
back to the v3 step-level format with category tags. Clearly labeled at
the top: `⚠ No task match — using step-by-step decomposition`.

### 7.3 Rejection handling

Same as v3: user submits feedback, session retries Phase 1a + 1b with
feedback prepended. Unlimited retries.

## 8. Phase 2a — Pattern composition (DEFERRED in Path B)

The original §8 specified a `tools/task_composer.py` module that consumed
matched tasks + slot values + scaffold map and produced a pre-wired
skeleton. **Path B does not include the composer.** The skeleton is built
by the existing v3 `run_skeleton_builder()` from `decomposition.steps`,
exactly as in v3.

The original §8 design (composer logic, container composition rules,
slot substitution modes, unfilled-slot handling, telemetry events) is
preserved as-is below as the eventual end state. Implementing it requires:

1. Completing T2 taxonomy review (composite phrases + scaffold bindings)
2. Building `data/task_scaffold_map.json`
3. Building `tools/task_composer.py`
4. Modifying §9 to remove pattern matching and skeleton building (which
   the composer would replace)

### 8.1 Purpose (v4 vision)

Given an approved task sequence with filled slots, produce the workflow
skeleton by composing each task's scaffold. Deterministic — no LLM.

### 8.2 Composition logic (v4 vision)

New module: `tools/task_composer.py` → `compose_skeleton(match_result,
slot_values) -> dict`.

For each matched task:

1. Load its `scaffold_pattern_id` from `task_scaffold_map.json`
2. Load the scaffold from `pattern_library.json`
3. Substitute slot*values into the scaffold's `PARAM*\*` placeholders
4. Append to the growing skeleton, wrapping in control flow as the
   scaffold dictates (containers compose into containers)

### 8.3 Container composition rules (v4 vision)

Some task patterns are **containers** (wrap other tasks). Examples:

- `iterate_rows` scaffold is a `WhileActivity` whose body is a slot for
  other tasks' activities
- `branch_decision` scaffold is an `IfElseActivity` with branch-1 and
  branch-2 slots

The composer maintains a container stack. When a container task appears,
subsequent non-container tasks compose into its body slot until another
container appears or the sequence ends.

Taxonomy marks each task as `composes_as: "linear" | "container" |
"container_member"`.

### 8.4 Slot substitution (v4 vision)

Two substitution modes:

- **Direct value substitution.** Slot value is a literal string → replace
  `PARAM_TableName` with "serverList".
- **xName reference substitution.** Slot value references another
  activity's output → replace `PARAM_HostName` with `%getCellValue1%`.

The slot_schema in the taxonomy specifies which mode per slot.

### 8.5 Unfilled slots (v4 vision)

If a slot_value is null (Decomposer couldn't determine from prompt), the
composer:

1. Leaves the corresponding field empty in the scaffold
2. Registers a placeholder in the warnings list for Gate 2
3. Does NOT invent a value

User resolves at Gate 2 via the same inline widget used today for
placeholder activities.

### 8.6 Telemetry events (v4 vision)

- `task_pattern_composed` — { task_id, scaffold_pattern_id, slots_filled,
  slots_unfilled, composition_duration_ms }

## 9. Phase 2b — Deterministic middle

### 9.0 Path B scope (v4.2)

**The Path B deterministic middle is the v3 deterministic middle plus
catalog enrichment, system bias, and telemetry wiring.** No stages were
removed because the composer that would have replaced them does not
exist. The v3 stages run in this order:

| Stage | Function               | Status in Path B     |
| ----- | ---------------------- | -------------------- |
| 2     | `run_pattern_match`    | unchanged            |
| 3     | `run_retrieval`        | + system bias (v4.1) |
| 4a    | `run_skeleton_builder` | unchanged            |
| 4b    | `run_enrichment`       | unchanged            |
| 4b.5  | `_backfill_table_vars` | unchanged            |
| 4c    | `run_fragments`        | unchanged            |
| 4c.5  | `run_content_scaffold` | unchanged            |
| 4c.6  | `run_wiring`           | unchanged            |

After Stage 4d (Wirer), additional stages run in `_run_post_wirer_stages`:
4f (re-fragments + scaffold), 4g (cleanup), 5 (annotation), 6 (validation),
7 (output).

The v4 vision in §9.1 (which removes pattern matching, skeleton building,
and most scaffold filling) describes the eventual state when the composer
ships.

### 9.1 What changes in v4 vision (deferred)

With the skeleton already structurally correct from Phase 2a, the
deterministic middle does less work. Removed:

- Pattern matching (the skeleton IS the pattern; no matching needed)
- Skeleton builder (skeleton exists)
- Most of scaffold filling (scaffolds already filled)

Retained _(also retained in Path B):_

- **Retrieval** — narrowed in v4. Path B runs full v3 retrieval.
- **Catalog enrichment.** Each activity in
  `data/activity_frequency.json` carries `task_type`, `module_type`,
  `node_type`, and `is_orphaned` fields, populated once at corpus
  ingestion by `scripts/merge_activity_info.py`. These fields are read
  at retrieval time but require no runtime computation. See §9.4 for the
  ingestion contract and Addendum B for the rationale.
- **Enrichment** — merge activity JSON syntax templates, enum values,
  field defaults (unchanged).
- **Table variable backfill** — unchanged.
- **Fragments F1-F9** — unchanged. Idempotent safety net that enforces
  structural invariants.
- **Content scaffold** — unchanged.
- **Immediate wiring** — unchanged.
- **Extended wiring** — unique-candidate rule preserved. Now rarer to
  fire because scaffolds pre-wire most fields. _(Path B: full v3 rate.)_
- **Tier 1 template passes** — unchanged (Description, ValueToDisplay,
  email Subject/To, ReturnValue conditions for status/boolean producers).

### 9.2 Modified retrieval (v4.1, deployed)

`tools/retrieval_tools.py` applies a multiplicative bias to candidate
`combined_score` based on agreement between the step's identified system
and the candidate's `module_type`:

| Condition                                                        | Multiplier | Constant             |
| ---------------------------------------------------------------- | ---------- | -------------------- |
| `extract_system_from_step(step)` matches `candidate.module_type` | ×1.5       | `SYSTEM_MATCH_BOOST` |
| Step has system, `candidate.module_type` is INTERNAL             | ×0.7       | `INTERNAL_PENALTY`   |
| Step has no identified system                                    | no-op      | —                    |

System identification is deterministic — `tools/system_extraction.py`
matches step text against a curated alias map of canonical system names
(ServiceNow, Jira, AWS, MsTeams, etc.). The bias is soft, not gating: a
strong keyword match for an INTERNAL activity can still win against a
weak system match. This degrades gracefully when `module_type` is missing
or wrong.

The bias does not change Layer 1 (intent map) behavior. Steps resolved
deterministically via `INTENT_TO_ACTIVITY` skip the 4-layer matcher and
therefore skip the bias.

The v4-vision `retrieve_for_task_position(task_id, position, slot_values)`
is deferred — task-canonical retrieval requires the composer.

### 9.3 Warnings surfaced at Gate 2

Three classes of warning carry through unchanged:

- Missing prerequisite
- Corpus-outlier wiring (`workflow_count < 5`)
- Template-filled mandatory field

The fourth class (unfilled slot from Phase 1b) is deferred — Path B has
no slots.

### 9.4 Catalog ingestion contract

The corpus ingestion pipeline runs `scripts/merge_activity_info.py`
exactly once per corpus snapshot, after `count_top_activities.py`
produces `activity_frequency.json` and the catalog metadata CSV
(`activity_info.csv`) is generated. The merge:

1. Joins the two sources on activity name (case-insensitive, instance
   digits stripped)
2. Resolves within-group conflicts by preferring non-INTERNAL
   `module_type` over INTERNAL
3. Applies evidence-based prefix overrides for activities mistagged
   INTERNAL whose name prefix is provably system-bound (e.g. `SN*`
   → ServiceNow, `Aws*` → AWS), gated on bidirectional witness +
   coverage thresholds
4. Writes the enriched catalog in place with a `.bak` backup
5. Emits `merge_review.json` with a complete audit trail of fixes,
   confidence-tagged prefix rules, and no-evidence flags for human
   review

Ingestion-time only — no runtime invocation. Missing `module_type`
values do not fail the pipeline; they cause the system bias to no-op
for that candidate.

## 10. Gate 2 — Activity list + data flow

### 10.1 Preview rendering

Activity-level view with task anchors:

Task 1: Load server list from Excel
  1. [Files/Folders] ReadXLS             — Read the server list

## 11. Phase 3 — Narrowed Wirer + artifacts

### 11.0 Path B scope (v4.2)

The Wirer in Path B is narrowed compared to v3 but less narrowed than
v4 vision (v4 expected scaffolds to pre-fill most things). What's been
done so far:

- **(v3 carryover)** Wirer is invoked AFTER the deterministic middle has
  run F1-F9 fragments, content scaffolds, and immediate/extended wiring
- **(Phase E patch 1, v4.2)** `max_tokens` raised from 8192 → 16384 to
  prevent silent truncation on `while_ifelse` workflows

### 11.5 Discovered Wirer issues (Phase E findings)

During Phase E end-to-end verification, three Wirer-related issues
surfaced. All have band-aids; all need permanent fixes in Phase G:

**Issue 1: Wirer truncation on long outputs.** With `max_tokens=8192`,
`while_ifelse` workflows produced incomplete JSON. Patched (Patch 1) by
raising to 16384. Permanent fix requires either further raising or
restructuring the Wirer to operate on smaller scopes.

**Issue 2: Activity count guard blocked retry.** When the Wirer dropped
activities and tripped the guard, `_check_needs_retry` didn't recognize
the failure pattern. Patched (Patch 2) by adding a check for
"truncated" / "returned 0 activities" error strings. Works but fragile —
better fix in Phase G is to make the guard's failure go through the
standard validation_invalid retry path.

**Issue 3: Wirer set `xName=CustomTypeName` on nested sub-objects,
breaking uniqueness validation.** Band-aided by adding explicit
instructions and worked examples to the Wirer prompt. Real fix in Phase G
is to generate these xNames deterministically in the fragments stage so
the Wirer never touches them.

**Issue 4: Wirer omitted `Description`/`description` fields on nested
Advanced/Result sub-objects, failing validation.** Band-aided by adding
template strings and explicit examples to the Wirer prompt. Real fix
depends on the validator review (Phase G): if the validator is correct,
deterministically populate these in the fragments stage; if the
validator is over-strict, remove the check.

## 16. Risks and mitigations

**R1: Task taxonomy is wrong.** Users have intents that no task covers,
or tasks are too coarse/fine.
_Mitigation:_ Unmatched-segments telemetry + Decomposer freeform always
runs. Weekly review of `unmatched_segments` field in `task_match_result`
events. Path B: low risk since matcher output is display-only.

**R2: Composite task match picks wrong composite.**
_(Deferred — Path B has no composites.)_

**R3: Scaffold substitution produces invalid workflows.**
_(Deferred — Path B has no composer.)_ Existing pattern-matching +
fragments path is the unchanged v3 risk.

**R4: Decomposer slot filling hallucinates values.**
_(Deferred — Path B has no slot filling.)_ Freeform Decomposer's existing
v3 hallucinations remain — may add steps not asked for, drop steps that
were asked for. Mitigated by Gate 1 (user catches before Phase 2 runs).

**R5: Container composition misnests tasks.**
_(Deferred — Path B has no composer.)_ Skeleton builder's existing v3
container handling is the unchanged risk.

**R6: Task review is expensive and nobody does it.**
_Mitigation in Path B:_ scope reduced to 10 atomic tasks with explicit
review, all `needs_review: false`. Future composite expansion is
optional.

**R7: Fallback mode is actually better than task mode.**
_(Path B note: matcher output doesn't affect generation, only display.
This risk is moot until composer ships.)_

**R8: Session loss on restart.**
_Mitigation:_ Documented. Beta scope.

**R9: System bias produces false positives on short or generic prefixes.**
Catalog has confirmed cases where the same prefix maps to multiple
intents (e.g. `ms*` matches both MsTeams activities and generic
Microsoft-prefixed customs like `msToken`).
_Mitigation:_ Bias is multiplicative and soft. Wrong system tag costs
only a 1.5× boost to a candidate that probably shouldn't have won
anyway. Confidence-tagged prefix rules in `merge_review.json` flag
short-prefix rules for human review at ingestion time.

**R10: Catalog `module_type` drifts from reality as the platform
evolves.**
Activities not yet in `activity_info.csv` get `module_type: None` and
skip the bias entirely.
_Mitigation:_ No-op behavior on missing data is the correct default.
Re-running `merge_activity_info.py` against an updated CSV refreshes
the catalog without code changes.

**R11: Wirer band-aids regress as Wirer prompt evolves _(v4.2)_.**
The two band-aids (xName uniqueness + Description population) work
today but depend on the Wirer following long instructions reliably.
Future Wirer prompt edits could weaken either.
_Mitigation:_ Phase G1 moves both responsibilities out of the Wirer into
deterministic stages. Until then, monitor `correction_fired` event rate
in telemetry — a sustained spike suggests one of the band-aids has
weakened.

**R12: Wirer truncation on workflows >5 top-level activities _(v4.2)_.**
`max_tokens=16384` accommodates today's `while_ifelse` workflows but a
larger workflow could truncate again. The activity count guard's retry
path is the safety net but adds cost and latency.
_Mitigation:_ Telemetry tracks `wirer_call.duration_ms` and the activity
count guard fires `generation_failed` events that include state dumps.
A pattern of guard failures on specific workflow shapes signals where
the Wirer needs to be further narrowed (Phase G1) or replaced piecewise.

## Addendum B: System bias rationale _(v4.1, unchanged)_

**Problem.** Raw catalog usage counts are dominated by INTERNAL plumbing
activities — `MemorySet`, `IfElseBranchActivity`, `CustomWorkflow`,
`DisplayValue` — which collectively account for ~98% of all corpus usage.
A retriever that ranks purely on usage frequency or co-occurrence will
prefer these generics over system-bound activities (`SNGetRecord`,
`MsTeamsSendMessage`, `JiraCreateIssue`) for steps that explicitly target
external systems. In v3 this caused observable misranks on cross-system
workflows.

**Why this is a soft signal in v4.** Most retrieval in v4 is bypassed
entirely — task scaffolds pin the activity at composition time. The
4-layer matcher only fires for flex slots (where the scaffold author
explicitly delegated activity choice) and for the freeform fallback path
(when no task matches). System bias improves both.

In Path B, retrieval is NOT bypassed because there's no composer. System
bias therefore applies to every retrieval call, not just flex slots.
Effect is similar — the bias modulates ranking on a continuous scale —
but the constants may need different tuning when bias fires more often.

**Why multiplicative, not gating.** Three reasons:

1. The catalog's `module_type` field is imperfect. Some activities are
   mistagged INTERNAL despite being clearly system-bound (the SN-prefix
   class). The merge script fixes the obvious cases but cannot fix
   prefixes with no in-data witnesses (e.g. `Corrigo*`, `ServiceDeskPlus*`
   were 100% INTERNAL in the source data). A hard filter would silently
   exclude legitimate candidates.
2. Some prompts mention a system contextually but want a generic
   activity (e.g. "log the ServiceNow ticket ID" wants `DisplayValue`,
   not an SN activity). A boost lets generics still win when keyword
   evidence overwhelms the bias.
3. Future-proofing: the multipliers can be tuned (or zeroed) without
   structural code changes. A gating filter would be harder to roll back.

**What the bias does not do.** It does not:

- Override Layer 1 intent-map decisions (those are deterministic and
  pre-bias)
- Filter candidates (no exclusion, only re-ranking)
- Affect task-canonical positions (those skip the 4-layer matcher
  entirely) _(N/A in Path B — no task-canonical positions)_
- Use `task_type`, `node_type`, or `is_orphaned` from the enriched
  catalog (those fields are stored for future use; no current consumer)

**Tuning surface.** `SYSTEM_MATCH_BOOST` and `INTERNAL_PENALTY` are
module-level constants in `tools/retrieval_tools.py`. Initial values
(1.5 / 0.7) are unvalidated guesses; expected to be tuned against eval
results once flex slots and fallback runs produce a workable sample
size. Telemetry already captures `selected_activity` and the candidates
list per step, which is sufficient for offline tuning without
instrumentation changes.

## Addendum C: Path B implementation history _(v4.2, NEW)_

This addendum documents what was built, what was deferred, what was
discovered during implementation, and the rationale for each decision.
It is the authoritative record of the system as it exists at the close
of the Path B implementation sessions.

### C.1 Why Path B

Reviewing the existing taxonomy at the start of Phase B revealed:

- 25 of 25 composite task drafts had empty `prompt_phrases` arrays
- 10 of 36 atomic task drafts had empty `prompt_phrases` arrays
- `task_scaffold_map.json` did not exist
- No composite carried a `scaffold_pattern_id` or `slot_schema`

Building full v4 would have required ~1–2 days of T2 review for
composite phrases and descriptions, ~2–4 hours of scaffold-binding work,
and an untested composer. None of that work was blocking — there was
no available reviewer with the right context — and the critical path
to user-visible value (telemetry, gates, preview, Mermaid, outcome
reporting) didn't depend on it.

Path B was the decision to ship the user-visible half without the
upstream investment. The architectural half remains accessible later by
completing T2 + building the composer.

### C.3 Discovered issues and their patches

Three issues surfaced during Phase E end-to-end verification that were
not in the original spec:

**1. Wirer truncation (Patch 1).** `max_tokens=8192` truncated
`while_ifelse` workflow JSON output. Fixed by raising to 16384.
Documented in §11.5 Issue 1.

**2. Activity count guard blocked retries (Patch 2).** When the Wirer
dropped activities, the guard set `output_result.status = "failed"`
with no path through `_check_needs_retry`. Fixed by recognizing
"truncated" / "returned 0 activities" error patterns.
Documented in §11.5 Issue 2.

**3. Wirer set xName=CustomTypeName on nested sub-objects (band-aid).**
Wirer was responsible for nested xName generation but used the
CustomTypeName itself (e.g., `xName="Advanced"`), creating duplicates
the validator rejected. Band-aided by adding instructions and worked
examples to the Wirer prompt. Phase G1 fix: move generation to the
deterministic middle. Documented in §11.5 Issue 3.

**4. Wirer omitted Description/description on nested sub-objects
(band-aid).** Same root cause as Issue 3 — Wirer responsibility for
fields that should come from somewhere else. Band-aided. Phase G1
fix depends on the corpus diagnostic. Documented in §11.5 Issue 4.

### C.6 Operational notes for Phase G

**Telemetry filenames use UTC.** Shell commands looking at log files
must use `date -u +%Y-%m-%d`, not `date +%Y-%m-%d`. This bit us once
during verification. Document in the README during Phase I.

**Smoke-test events pollute aggregate counts.** Running
`python -m tools.telemetry` fires one of every 24 event types. When
querying real-pipeline event counts via `jq | sort | uniq -c`, mentally
subtract the smoke baseline or filter by session_id pattern.

**State dumps are large.** Each `_log_fatal` invocation writes the full
session state to `logs/state_dumps/`. For Phase G prompts that exercise
correction paths, the dump directory will grow. Consider periodic
cleanup or a state-dump retention policy in Phase I.

**Test files were not created.** Per working agreement, the spec's §19
file list is the source of truth, and `tests/test_*.py` files were
explicitly skipped. Phase G1's nested xName generator should ship with
at least a smoke test in the same `if __name__ == "__main__"` style as
the other tools modules — but not as a `tests/` file.
