# Workflow Generator — Completion Spec (v4)

## 0. Document status and audience

Authoritative spec for the workflow generator's task-centered, three-stage
gated flow. Supersedes v3. Folds in:

- Task taxonomy as structural backbone (from the task mining work)
- Variant C patterns bringing pre-wired skeletons per task
- Narrowed Decomposer scope (slot filling, not structure)
- Internal-beta scope (terser UX, telemetry-first, desktop-only)
- Tier 1 determinism additions (template passes)
- Three-gate architecture with Mermaid viz
- No LLM prompt validator (six deterministic checks only)
- Telemetry as product, not polish

Companion documents for history:
- `determinism_analysis.md`
- `plan_review_accuracy_focus.md`
- `frontend_beta_design.md`
- `finished_product_review.md`
- `task_mining_report.md` (generated by `mine_task_taxonomy.py`)

Primary goal: **produce accurate workflows by matching prompts to tasks
first, letting task patterns bring pre-wired structure, and narrowing the
LLM's role to slot filling and edge cases.** Telemetry measures how well
this works.

---

## 1. Architectural thesis

### 1.1 The core idea

Today's pipeline decomposes a prompt into arbitrary steps, then retrieves
activities per step, then tries to wire them. Each stage has variance. The
variances compound — Decomposer picks wrong intent, retriever picks wrong
activity, wiring picks wrong predecessor.

The v4 pipeline inverts this. It matches the prompt to **tasks** first,
where each task owns a **pre-wired pattern**. Task patterns bring
structure, members, and wiring as a unit. The LLM's job shrinks to filling
slots (specific values the prompt mentions) in already-correct structures.

### 1.2 Why this matters for accuracy

Tasks as the primary matching unit makes three failure modes rarer:

**Wrong activity choice.** Retrieval today picks between Ping and
TraceRoute on keyword overlap. Task-scoped retrieval narrows the choice:
if the task is "check connectivity," Ping is the canonical member; if the
task is "diagnose network path," TraceRoute is.

**Wrong wiring.** Extended wiring today risks silent-wrong picks when
multiple candidates match. Task patterns pre-specify wiring ("iterate
rows" always wires ExitWhile.Counter to the preceding GetRowsCount),
eliminating ambiguity.

**Structural mismatch.** Decomposer today produces arbitrary step lists
that may not match a valid pattern. Task matching produces sequences of
known-good patterns that compose into valid structures by construction.

### 1.3 Why this matters for UX

Gate 1 becomes legible. Instead of:

```
1. Create a table          [Tables]
2. Read server list        [Files/Folders]
3. Count servers           [Tables]
4. For each server         [Flow Control]
   4a. Get server name     [Tables]
   4b. Ping                [Network]
   4c. Check result        [Flow Control]
        4c.1. Send email   [Communication]
```

It reads:

```
Plan (3 tasks):

  1. Load server list from Excel
     → reads Excel file, builds table, counts rows
  2. Check each server
     → iterates rows, pings each, captures result
  3. Notify on failure
     → branches on ping result, sends email on failure
```

The user confirms intent at the task level, not the activity level. They
can still drill down via `[Show raw]` if they want to see activities.

## 4. Phase 0 — Prompt validation

Unchanged from v3. Six deterministic checks. No LLM validator. See v3 §4
for the complete list — reproduced here for completeness:

1. Length (≥10 chars initial, ≥5 feedback)
2. Character diversity (≥5 distinct, unique/total ratio ≥ 0.3)
3. Consonant run (no 6+ consecutive consonants)
4. Domain keyword (≥1 from 60-word vocabulary)
5. Session freshness (4-hour timeout)
6. Prompt-per-session limit (50 max, runaway protection only)

Implementation module: `tools/prompt_validator.py`. Backend and frontend
both run checks 1-4; backend adds 5-6.

## 5. Phase 1a — Task matching (NEW)

This is the architectural centerpiece of v4.

### 5.1 Purpose

Given a validated prompt, produce an **ordered sequence of task_ids**
that this workflow accomplishes. Deterministic — no LLM. Output feeds
both the narrowed Decomposer (Phase 1b) and the pattern composer
(Phase 2a).

### 5.2 Data dependencies

Three data files, produced by `scripts/mine_task_taxonomy.py` and then
hand-reviewed:

**`data/task_match_phrases.json`** — flat map of task_id → prompt phrases,

```json
      "check_target": "PARAM_HostName",
      "notification_recipient": "PARAM_To",
      "notification_condition": "PARAM_Formula"
    }
  },
  ...
}
```

### 5.3 Matching algorithm

New module: `tools/task_matcher.py` → `match_tasks(prompt: str) -> TaskMatchResult`.

Priority-ordered matching:

**1. Composite task match first.** For each composite task, score the
prompt against its `prompt_phrases` using substring + word-boundary match.
Any composite task with ≥2 matching phrases is a strong candidate.
Composites win over atomics because they encode more intent.

**2. Atomic task match for gaps.** After composite matches are identified,
scan the prompt for phrases from atomic tasks that weren't covered. These
fill in remaining intent (e.g., "also send a summary email at the end"
might trigger `send_email` atomic after a composite.

**3. Order inference.** Tasks matched are ordered by their first phrase
occurrence in the prompt. If the prompt says "ping each server then send
email," the matcher emits `[query_system_state, send_email]` in that order.

**4. Confidence scoring.** Each matched task gets:
- `confidence`: 0.0–1.0 based on phrase match strength and specificity
- `match_reasons`: list of matched phrase strings
- `source`: "composite" | "atomic"

**5. Fallback on no match.** If zero tasks match, return
`{tasks: [], fallback: "use_decomposer_freeform"}`. The Decomposer runs
in its old freeform mode for that prompt. Telemetry flags this for
taxonomy review.

### 5.4 Output schema

```python
@dataclass
class TaskMatchResult:
    tasks: list[MatchedTask]              # ordered by prompt position
    fallback: str | None                  # "use_decomposer_freeform" | None
    unmatched_segments: list[str]         # prompt fragments no task claimed
    total_confidence: float               # average across matched tasks

@dataclass
class MatchedTask:
    task_id: str
    kind: str                             # "atomic" | "composite"
    confidence: float
    match_reasons: list[str]
    slot_values: dict[str, str]           # filled by Phase 1b (Decomposer)
    prompt_span: tuple[int, int]          # char range in prompt
```

`slot_values` starts empty; the Decomposer fills it in Phase 1b.

### 5.5 Performance

Pure Python regex and substring matching over ~50 task phrase lists.
Expected latency: <50ms for typical prompts. No LLM call.

### 5.6 Telemetry events

- `task_match_attempted` — { prompt_length, total_phrases_scanned }
- `task_match_result` — { tasks, confidence, fallback, unmatched_segments }

## 6. Phase 1b — Decomposer (narrowed)

### 6.1 New role: slot filling, not structure

The Decomposer no longer produces an arbitrary step list. Its job:

- Given: the original prompt + matched task sequence (with slot schemas)
- Produce: the same task sequence with `slot_values` filled in from the
  prompt
- Optional: a `workflow_summary` one-liner for Gate 1 preview

The Decomposer doesn't decide structure. It doesn't pick activities. It
binds concrete values from the prompt to the abstract slots each task
defines.

### 6.2 Instruction

New instruction in `agents/decomposer_agent.py`:

```
You are given:
1. A user's workflow prompt
2. An ordered sequence of matched tasks, each with:
   - task_id
   - label
   - slot_schema: a dict of slot names and what they mean

For each task, fill in the slot_values from the prompt. If a slot isn't
answerable from the prompt, leave it as null and the user will resolve it
at Gate 2.

Do not:
- Add or remove tasks
- Reorder tasks
- Decide activities
- Invent slot values not grounded in the prompt

Return:
{
  "workflow_summary": "one-line summary of the whole workflow",
  "matched_tasks": [
    {
      "task_id": "...",
      "slot_values": {
        "slot_name": "value from prompt or null"
      }
    },
    ...
  ]
}
```

### 6.3 Fallback path

When Phase 1a returned `fallback: "use_decomposer_freeform"`, the
Decomposer runs in its v3 mode: freeform step decomposition with the old
instruction. Output flows directly into Gate 1 as before. Telemetry
marks these sessions distinctly.

### 6.4 Telemetry events

- `decomposer_call` — { duration_ms, prompt_tokens, output_tokens,
  mode: "slot_filling" | "freeform_fallback" }
- `task_slot_filled` — { task_id, slots_filled, slots_null }

## 8. Phase 2a — Pattern composition (NEW)

### 8.1 Purpose

Given an approved task sequence with filled slots, produce the workflow
skeleton by composing each task's scaffold. Deterministic — no LLM.

### 8.2 Composition logic

New module: `tools/task_composer.py` → `compose_skeleton(match_result,
slot_values) -> dict`.

For each matched task:

1. Load its `scaffold_pattern_id` from `task_scaffold_map.json`
2. Load the scaffold from `pattern_library.json`
3. Substitute slot_values into the scaffold's `PARAM_` placeholders
4. Append to the growing skeleton, wrapping in control flow as the
   scaffold dictates (containers compose into containers)

### 8.3 Container composition rules

Some task patterns are **containers** (wrap other tasks). Examples:

- `iterate_rows` scaffold is a `WhileActivity` whose body is a slot for
  other tasks' activities
- `branch_decision` scaffold is an `IfElseActivity` with branch-1 and
  branch-2 slots

The composer maintains a container stack. When a container task appears,
subsequent non-container tasks compose into its body slot until another
container appears or the sequence ends.

Taxonomy marks each task as `composes_as: "linear" | "container" |
"container_member"`.

### 8.4 Slot substitution

Two substitution modes:

- **Direct value substitution.** Slot value is a literal string → replace
  `PARAM_TableName` with "serverList".
- **xName reference substitution.** Slot value references another
  activity's output → replace `PARAM_HostName` with `%getCellValue1%`.

The slot_schema in the taxonomy specifies which mode per slot.

### 8.5 Unfilled slots

If a slot_value is null (Decomposer couldn't determine from prompt), the
composer:
1. Leaves the corresponding field empty in the scaffold
2. Registers a placeholder in the warnings list for Gate 2
3. Does NOT invent a value

User resolves at Gate 2 via the same inline widget used today for
placeholder activities.

### 8.6 Telemetry events

- `task_pattern_composed` — { task_id, scaffold_pattern_id, slots_filled,
  slots_unfilled, composition_duration_ms }

## 9. Phase 2b — Deterministic middle (simplified)

### 9.1 What changes

With the skeleton already structurally correct from Phase 2a, the
deterministic middle does less work. Removed:

- Pattern matching (the skeleton IS the pattern; no matching needed)
- Skeleton builder (skeleton exists)
- Most of scaffold filling (scaffolds already filled)

Retained:

- **Retrieval** — narrowed. For each activity position in the skeleton,
  confirm the task's canonical member is valid. Only run the 4-layer
  matcher when a position is a generic slot ("this task can use any
  matching activity").
- **Enrichment** — merge activity JSON syntax templates, enum values,
  field defaults (unchanged).
- **Table variable backfill** — unchanged.
- **Fragments F1-F9** — unchanged. Idempotent safety net that enforces
  structural invariants.
- **Content scaffold** — unchanged.
- **Immediate wiring** — unchanged.
- **Extended wiring** — unique-candidate rule preserved. Now rarer to
  fire because scaffolds pre-wire most fields.
- **Tier 1 template passes** — unchanged (Description, ValueToDisplay,
  email Subject/To, ReturnValue conditions for status/boolean producers).

### 9.2 Modified retrieval

New behavior in `tools/retrieval_tools.py`:

```python
def retrieve_for_task_position(task_id: str, position: int,
                                 slot_values: dict) -> ActivityChoice:
    """
    For a task-aware position, use the task's canonical members as the
    candidate set instead of scoring the full 655-activity list.
    """
```

When a position is task-canonical (the scaffold pinned the activity type,
e.g., "the WhileActivity in iterate_rows"), retrieval confirms the match
and skips the 4-layer scoring. Only positions marked as flex (the
scaffold has `PARAM_activity_type`) run full retrieval.

### 9.3 Warnings surfaced at Gate 2

Three classes of warning carry through unchanged:
- Missing prerequisite
- Corpus-outlier wiring (`workflow_count < 5`)
- Template-filled mandatory field

New class added:
- **Unfilled slot from Phase 1b** — surfaced as "slot 'X' in task Y is
  empty; the user should provide value or accept placeholder"

## 11. Phase 3 — Narrowed Wirer + artifacts

### 11.1 Even narrower scope

With task scaffolds handling most wiring, the Wirer's job shrinks
further. In v4 it only fills:

- SendEmail.Body (free-form content)
- TSQL/PowerShell scripts
- Scalar-producer ReturnValue conditions with prompt-grounded thresholds
- Sanity check on the composed skeleton

No activity swapping. No structural changes. No filling of anything
covered by task scaffolds or Tier 1 templates.

### 11.2 Accuracy validator

Unchanged from v3. VERIFY notes for:
- Mandatory fields filled by templates
- Corpus-outlier wiring
- High placeholder ratio
- Empty scalar-producer ConditionType

New classes for v4:
- Unfilled slot that should have been filled by Decomposer
- Scaffold parameter that wasn't substituted

### 11.3 Mermaid diagram

Generated as in v3. Progressive updates at each gate. Task groupings
appear as subgraph boxes in the diagram.

### 11.4 Outputs

Same as v3: JSON, XML, Mermaid. Tracking token for post-import outcome
reporting.

### 13.3 Taxonomy-quality telemetry queries

Task-specific questions the data answers:

- **Which tasks never match any prompt?** → audit taxonomy, add
  phrase variations
- **Which composite tasks have lowest confidence?** → refine scaffolds
- **Which unmatched segments recur?** → add new tasks to taxonomy
- **Which slots does the Decomposer fail to fill?** → prompt ambiguity
  or slot schema unclear
- **Which scaffolds fail composition?** → scaffold bugs or taxonomy
  mismatch
- **Does fallback-mode accuracy match task-mode accuracy?** → measures
  the value of the task layer

## 14. Open decisions (all resolved)

| Decision | Choice | Rationale |
|---|---|---|
| Task taxonomy authoring | Corpus-mined draft + manual curation | Best of both |
| Task match algorithm | Deterministic phrase matching | Fast, no LLM dependency |
| Composite vs atomic priority | Composites first | Encode more intent |
| Fallback when no task matches | Run v3-style freeform Decomposer | Graceful degradation |
| Decomposer in task mode | Slot filling only, no structure | Narrower = more reliable |
| Scaffold reuse | Leverage existing pattern_library.json | Already corpus-validated |
| Container composition | Explicit `composes_as` per task | Avoids heuristic bugs |
| Unfilled slots | Surface at Gate 2 as placeholders | User resolves explicitly |
| Gate 1 default view | Task-level | Legible; `[Show activities]` drills down |
| Retry caps | None | Internal beta captures retry signal |
| Prompt validator | 6 deterministic only | Internal users don't submit junk |
| Mobile support | Deferred | Desktop only |
| Post-import outcome | Buttons + optional Slack hook | Level 2+ accuracy signal |
| Mermaid diagrams | Kept, with task subgraphs | User verification + telemetry |

## 15. Implementation sequence

Ten phases. ~9 days total. Taxonomy work must finish before pipeline
integration.

**Phase T1 — Taxonomy draft (half day)**
- Run `scripts/mine_task_taxonomy.py` against corpus
- Generate `task_taxonomy_draft.json`, `task_match_phrases_draft.json`,
  `task_mining_report.md`
- Done when all three files exist, report reviewed.

**Phase T2 — Taxonomy review (1-2 days)**

## 16. Risks and mitigations

**R1: Task taxonomy is wrong.** Users have intents that no task covers,
or tasks are too coarse/fine.
*Mitigation:* Unmatched-segments telemetry + fallback to freeform
Decomposer. Weekly review of fallback rate. Target: <10% of prompts.

**R2: Composite task match picks wrong composite.**
*Mitigation:* Telemetry shows confidence distributions. Low-confidence
matches trigger Gate 1 review by the user. Phrase lists refined based
on rejection feedback.

**R3: Scaffold substitution produces invalid workflows.**
*Mitigation:* Fragments F1-F9 run after composition as safety net.
Accuracy validator catches residuals. Correction pipeline as final
fallback.

**R4: Decomposer slot filling hallucinates values.**
*Mitigation:* Explicit "leave null if not in prompt" instruction.
Unfilled-slot telemetry tracks hallucination rate. Null slots become
placeholders at Gate 2, not invented values.

**R5: Container composition misnests tasks.**
*Mitigation:* Explicit `composes_as` per task. Composer has unit
tests for all container/member combinations. Fragment F-series enforces
container invariants.

**R6: Task review is expensive and nobody does it.**
*Mitigation:* Miner produces draft with most fields pre-filled. Review
is edit-in-place in one JSON file. Estimated 1-2 days total for
full review. Can be chunked.

**R7: Fallback mode is actually better than task mode.**
*Mitigation:* Track accuracy by mode. If fallback consistently wins,
revisit taxonomy. Possible the taxonomy is too rigid for real usage.

**R8: Session loss on restart.**
*Mitigation:* Documented. Beta scope.

## 18. Success criteria

The completion is done when:

1. A team member submits a prompt → sees task-level Gate 1 preview in
   ~25s.
2. Task matcher correctly identifies tasks for 80%+ of test prompts.
3. User can iterate freely on all gates without caps.
4. Gate 2 shows activities grouped by task.
5. Downloads produce JSON, XML, Mermaid.
6. Post-import outcome one-click reporting works.
7. All user actions generate telemetry events.
8. Weekly review answers taxonomy-quality questions via `jq`.
9. Fallback mode works gracefully for prompts with no task match.
10. Generated XML imports cleanly for 5 test prompts covering different
    task sequences.

## Appendix A: Worked example

To make the architecture concrete, here's one prompt traced end to end
through v4.

**Prompt:** "Every morning, check a list of servers from an Excel file.
For each server, ping it. If the ping fails, send an email to the admin
with the server name."

**Phase 0 (validation):** Passes all 6 checks. Proceed.

**Phase 1a (task matching):** Matcher scans prompt phrases:
- "check a list of servers" → matches composite
  `composite_read_iterate_check_notify` (high confidence)
- No remaining atomic-only phrases

Output:
```json
{
  "tasks": [
    {
      "task_id": "composite_read_iterate_check_notify",
      "confidence": 0.89,
      "slot_values": {}  // to be filled by Decomposer
    }
  ],
  "fallback": null
}
```

**Phase 1b (Decomposer slot filling):** LLM fills slots:
```json
{
  "workflow_summary": "Every morning, ping servers from an Excel list and email admin on failure.",
  "matched_tasks": [
    {
      "task_id": "composite_read_iterate_check_notify",
      "slot_values": {
        "source_variable": "server list from Excel file",
        "iteration_item": "each server",
        "check_target": "server ping status",
        "notification_recipient": "admin",
        "notification_condition": "ping failure"
      }
    }
  ]
}
```

**Gate 1 preview:**
```
Every morning, ping servers from an Excel list and email admin on failure.

Plan (1 task):

  1. Read, iterate, check, notify
     → Read the server list from Excel, iterate through each,
       check server ping status, email admin on ping failure

[Looks good]  [Needs changes]  [Show activities]  [Show raw]
```

User approves.

**Phase 2a (composition):** Composer loads scaffold `p019`, substitutes:
- `PARAM_TableName` → `serverList`
- `PARAM_xname_whileactivity` → `forEachServer`
- `PARAM_HostName` → `%getCellValue1%` (xName ref to in-scope GetCellValue)
- `PARAM_To` → `%adminEmail%` (with UPDATE note since not filled)
- `PARAM_Formula` → `=Equals(&&&,Failure)`

Output: complete pre-wired skeleton with 8 activities in correct nesting.

**Phase 2b (deterministic middle):** Runs fragments, enrichment,
templates. Catches nothing new because scaffold was already correct.
Tier 1 fills Description fields, ValueToDisplay, email Subject.

**Gate 2:** User sees activity-grouped preview, confirms. Generates
artifacts.

**Phase 3:** Wirer fills SendEmail.Body based on prompt content. Validates.
Emits JSON + XML + Mermaid.

**Gate 3:** Downloads available. User imports, clicks [✓ Worked].
Telemetry captures full lifecycle.

Total LLM calls: 2 (Decomposer slot fill, Wirer body fill). Compared to
v3: 3 calls (validator, Decomposer freeform, Wirer full fill). v4 is
cheaper and more reliable by construction.
